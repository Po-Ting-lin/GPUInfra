from access to release.

The cache avoids repeating H2D transfers for the same image. Follow an incoming frame to see where its data lives, when it can be reused, and how every failure path ends.

01

Separate the data, the index, and the lease

The scheduler selects a ready frame, a free task, and a NUMA-local worker before checking the cache. Cache residency does not change scheduling decisions.

Original CPU data

FrameCpuAtom owns the image and metadata. The key is (frameId, cameraId); the same frameId from different cameras produces different keys.

Keys need no preregistration. Between resets, the same key must identify the same immutable content.

GPU storage

StaticData owns the manager, which manages a fixed set of K entries. Each entry owns a persistent GPU buffer.

The framework establishes NUMA affinity before every task callback. load() selects the unique local GPU; zero or multiple GPUs cause an error. Each task also has its own d_input. When the cache cannot serve a request, the task uploads into this fallback buffer.

One access lease

GpuDataAccess records the buffer and stream used by this access. It owns neither the allocation nor the stream.

A live cache lease prevents its entry from being evicted. A live fallback lease also blocks reset / release.

Three entry states; for Valid entries, the reader count matters too

“Active” is not a fourth entry state. Loading counts a fill lease; Valid counts reader leases. Only entries that are Valid with zero active accesses belong to the evictable LRU list.

Getting data: follow this decision order

StaticData::getCacheData(metadata, resources) validates the fixed layout before calling GpuCacheManager::acquire(). A miss may reserve a cache fill or use fallback.

① Valid input and resources?

No → Invalid Stop. Yes → Look up the complete key.

② Key already indexed?

Yes, but metadata differs → Invalid

Yes, state is Loading → TaskFallback

Yes, Valid with a usable replica on this GPU → CacheHit

Yes, Valid but the local GPU replica is unavailable → TaskFallback

No → Look for an available entry.

③ Any Empty entry?

Yes → CacheFill Create the key mapping and mark Loading. No → Check LRU.

④ Any idle LRU entry?

Yes → Remove the oldest key and reuse its buffer → CacheFill. No → TaskFallback (K = 0, or every entry is in use / Loading).

Invalid: input errors and defensive internal checks
  • StaticData: Not initialized, zero bytes, or bytes / width / height / dtype differ from the fixed layout established at initialization.
  • Manager: Not initialized or currently releasing; metadata bytes mismatch or nonpositive width / height; invalid or ineligible GPU ID; null stream / d_input; resources.inBytes mismatch. Valid fallback resources are required even when a cache hit is expected.
  • Existing key: Entry index out of bounds / null entry, mismatched metadata, state neither Loading nor Valid, or inconsistent active count and LRU membership.
  • Fill candidate: Missing GPU pointer, inconsistent Empty / Valid / active / LRU state, failure to erase the old mapping, or failure to insert the new mapping → restore the candidate and return Invalid. If insertion fails during replacement, the manager attempts to restore the old mapping; restoring a Valid candidate places it at MRU. If taking an LRU candidate fails to remove it from the list, the manager treats this as no available candidate and uses fallback.

Internal consistency errors should not occur after normal initialization while invariants hold. They differ from an ordinary full cache: normal capacity pressure uses fallback.

How does an unavailable local replica differ from the wrong GPU?

Each manager currently accepts one GPU. Resources targeting another GPU are rejected at the entrance with Invalid. If an eligible GPU has a Valid entry but lacks a pointer or valid replica, a defensive path uses fallback; normal single-GPU execution usually does not reach it. Cross-GPU replica fills / migration are future extensions and are not implemented.

04

Finishing: success determines what stays cached

freeCacheData(submittedSuccessfully) first synchronizes the task stream captured when access was obtained. Passing false or failing synchronization counts as failure; returning true also requires a valid lease and internal state.

A fill fails after eviction

Once the new key has obtained CacheFill, the old key is already evicted. If the new fill fails, the entry returns to Empty; the old cached data is not restored. Either key may be filled again on a later request.

Multiple simultaneous readers

Readers can coexist and are all read-only. Success, failure, or abort removes only that reader’s lease. The entry remains protected while any reader is still using it.

// Example: H2D, kernels, and D2H all use resources.stream.
GpuDataAccess access = staticData.getCacheData(metadata, resources);
if (!access) return false;

bool ok = true;
if (access.needsUpload()) {
    ok = enqueueH2D(access.writableData(), resources.stream);
}
if (ok) {
    ok = enqueueComputeAndD2H(access.data(), resources.stream);
}
// Call even after submission fails: synchronize queued work and end the lease.
if (!access.freeCacheData(ok)) return false;
// Collect D2H results here. The access pointers must no longer be used.
Repeated calls, publication failures, and synchronization boundaries

Call once on the normal path. Calling freeCacheData() on a default Invalid access or an already finished access returns false. Destruction of a reset access does not synchronize again. Access objects cannot be copied or moved.

If a fill cannot mark its replica valid or join LRU, it rolls back to Empty and returns false. The manager checks owner, key, pointer, bytes, state, and lease counts. Failed internal validation is not successful publication, and corrupted counts cannot be assumed repaired.

Normal finishing checks the CUDA synchronization result. Destruction is an error-path safety net: it attempts synchronization, logs CUDA errors, and then aborts, with no success result to return. It never publishes an unfinished fill as Valid. The cache mutex protects management state; CUDA work runs on each task stream, and finishing synchronizes outside the manager’s state lock.

Caller responsibilities: The success flag means the required H2D, compute, and D2H work was submitted correctly; the cache does not inspect image contents. If content changes for the same key, use a new identity or reset at a safe boundary first. Each task has one fallback input. When processing two inputs simultaneously, two live fallbacks must not overwrite each other. The current graph uses exclusive task checkout to prevent workers from concurrently reusing the same task.

A live fallback also blocks reset / release, including when K = 0. Reset at a quiescent phase / run boundary. Finish every access before shutting down its owner and task resources.

Lifecycle failures and retries

Initialization rejects repeated initialization, multiple GPUs, invalid GPU IDs / bytes, capacity overflow, or allocation failure. StaticData resolves its GPU from the current framework NUMA environment, rejecting zero or multiple local GPUs, and also checks fixed-layout bytes and available GPU memory. K = 0 is valid.

If reset preconditions fail, it returns false without clearing the cache. Manager release also returns false while a lease is live or another release is in progress. Repeating release after complete cleanup returns true.

If CUDA allocation release fails, release returns false. Entries with remaining allocations are retained for retry, and the manager stops providing new accesses. StaticData::release() sets its own initialized flag to false before calling the manager. Thus, even if a live lease causes rejection, no new access can be obtained through StaticData; finish existing leases, then retry release. The owner must outlive every access.

06

Fixed capacity, an ongoing stream of frames

N, K, and S count different things

N counts frames arriving over time; K counts GPU cache entries; S counts slots in the CPU residency table.

S = K == 0 ? 0 : nextPow2(2 × K)

The index stores only current Loading / Valid keys, at most K mappings. Eviction erases the old key and inserts a new one, so execution can continue when N exceeds K or S. The default is K = 4.

Hash collisions, deletion, and the full LRU rules

The residency table stores key → entryIndex. Keys hashing to the same slot use linear probing to find the complete key or an empty slot; an empty slot indicates a miss. Collisions do not make different cameras / frames share data. Erase uses backward shifting to preserve the probe chain, keeping later keys reachable.

For K > 0, S ≥ 2K, so at most half the slots are occupied. Loading entries also consume a mapping. Slots are allocated at initialization; the hot path never grows or rehashes the table. Lookups are O(1) on average and O(S) in the worst case; average complexity does not guarantee constant latency.

The Empty pool takes priority over LRU. Global LRU is a single list shared within this manager, independent of hash slot order; read it left to right as LRU → MRU. The first hit removes an entry; the last reader finishing returns it to MRU. A successful fill also joins MRU. Eviction order therefore depends on when leases end, not simply when requests arrive.

Eviction, failed fills returning to Empty, and reset never reallocate GPU buffers. The hot path has no cudaMalloc() / cudaFree(); allocation and release occur at lifecycle boundaries.
