GPU CACHE, STEP BY STEP

一份資料，
從取得到釋放。

Cache 的工作是讓相同影像少傳一次 H2D。從一個 frame 進來開始，看懂資料放在哪裡、何時能重用，以及每種失敗如何收尾。

01 / 取得

getCacheData()

檢查 layout、查找 key，取得可用的 cache 或 task buffer。

02 / 使用

需要時上傳，再運算

status() 告訴 caller 是否需上傳；getStream() 回傳 task stream；kernel 一律讀 access.data()。

03 / 收尾

freeCacheData(ok)

同步 stream，發布或回滾 fill，釋放這次存取權。

「free」結束的是這次存取。 GPU buffer 會保留供重用；呼叫後 access 與其指標失效。真正釋放 cache 配置的是 release()。

01

先分清楚：資料、索引、存取權

Scheduler 先選 ready frame、free task 與 NUMA-local worker，之後才查 cache。Cache residency 不會改變排程選擇。

CPU 原始資料

FrameCpuAtom 持有影像與 metadata。Key 是 (frameId, cameraId)；不同 camera 的相同 frameId 是不同 key。

不必預先註冊 key。兩次 reset 之間，相同 key 必須代表相同的不可變內容。

GPU 儲存空間

StaticData 擁有 manager；manager 管理固定 K 個 entry，每個 entry 擁有 persistent GPU buffer。

Framework 在每個 task callback 前建立 NUMA affinity；load() 選擇唯一的本地 GPU，零顆或多顆都報錯。Task 另有自己的 d_input。Cache 不可用時，用這個 fallback buffer 上傳。

一次存取權（lease）

GpuDataAccess 記錄本次使用哪個 buffer、哪條 stream。它不擁有配置，也不擁有 stream。

Lease 存活時，對應 cache entry 不可被淘汰；fallback lease 也會阻止 reset / release。

Entry 只有三種狀態；Valid 還要看使用人數
Entry 狀態使用人數同 key 再來能給其他 key 重用嗎？
Empty0尚無 mapping；可拿來填入可以，優先取用
Loading1 位 fill owner走 fallback；不等待填入者不可以
Valid 閒置0CacheHit，開始讀取可以，依 global LRU 淘汰
Valid 使用中1 位以上 readerCacheHit，可增加 reader不可以；最後一位離開才回 LRU

「Active」不是第四種 entry state。Loading 的數量是 fill lease；Valid 的數量是 reader leases。只有 Valid 且人數為 0 的 entry 在可淘汰 LRU 中。

03

取得資料：依這個順序判斷

StaticData::getCacheData(metadata, request) 先驗證固定 layout，再進入 GpuCacheManager::getCacheData()。Miss 可以填入 cache，也可以使用 fallback。

① 輸入與資源有效？

否 → Invalid停止。是 → 查完整 key。

② Key 已在索引？

有，但 metadata 不一致 → Invalid

有，狀態是 Loading → TaskFallback

有，Valid 且本 GPU replica 可用 → CacheHit

有，Valid 但本 GPU replica 不可用 → TaskFallback

沒有 → 尋找可用 entry。

③ 有 Empty entry？

有 → CacheFill建立 key mapping，標為 Loading。沒有 → 看 LRU。

④ 有閒置 LRU entry？

有 → 移除最舊 key，重用其 buffer → CacheFill。沒有 → TaskFallback（K = 0，或全部使用中 / Loading）。

回傳結果決定指標與 H2D
Statusdata() 指向Caller 需要填入？writableData()取得時的變化
CacheHitEntry 的 GPU bufferfalsenullptr（唯讀）Reader +1；第一位 reader 將 entry 移出 LRU
CacheFillEntry 的 GPU buffertrue同一 buffer先插入 mapping；Loading，active = 1，replica 尚無效
TaskFallbackTask 的 d_inputtrue同一 bufferFallback lease +1；不建立 cache mapping
Invalidnullptrfalsenullptr不得提交 GPU 工作；以 if (!access) 檢查
Invalid：輸入錯誤與內部防禦分支
  • StaticData：未初始化，或 bytes 為 0、bytes / width / height / dtype 不符合初始化時的固定 layout。
  • Manager：未初始化或正在 release；metadata bytes 不符、width / height 非正值；GPU ID 無效或不在允許清單；request.stream / request.d_fallback 為空；request.fallbackBytes 小於 cache payload。即使預期 cache hit，也要提供有效 fallback 資源。
  • 已有 key：entry index 越界 / entry 為空、metadata 不一致、狀態既非 Loading 也非 Valid，或 active count 與 LRU membership 不一致。
  • 填入候選：GPU pointer 缺失、Empty / Valid / active / LRU 狀態不符、舊 mapping erase 失敗，或新 mapping insert 失敗 → 歸還候選並回傳 Invalid。替換時 insert 失敗會嘗試還原舊 mapping；歸還 Valid 候選會加入 MRU。取 LRU 候選時若無法移出 list，則視為沒有候選而走 fallback。

在正常初始化與不變條件成立時，內部一致性錯誤不應發生。它們與一般「cache 滿了」不同：正常容量不足會使用 fallback。

本 GPU replica 不可用，和選到錯誤 GPU，有什麼差別？

目前每個 manager 只接受一顆 GPU。Resources 指向其他 GPU 會在入口被拒絕，回傳 Invalid。若允許的 GPU 對應到 Valid entry，卻缺少 pointer 或有效 replica，實作有 fallback 防禦路徑；正常單 GPU 流程通常不會觸發。跨 GPU replica fill / migration 是未來擴充，尚未實作。

04

收尾：是否成功，決定哪些資料能留下

freeCacheData(submittedSuccessfully) 會先同步取得 access 時的 task stream。傳入 false 或同步失敗都視為失敗；回傳 true 還需要 lease 與內部狀態有效。

三種有效 access × 三種結束方式
Access傳入 true，且同步成功傳入 false，或同步失敗未呼叫便析構（RAII abort）
CacheFill標記 replica 有效；Loading → Valid；active 歸零；加入 MRUErase 新 key；回 Empty；replica 無效；buffer 留著先嘗試同步，再 abort；回 Empty；即使 GPU 工作成功也不發布
CacheHitReader −1；最後一位離開時加入 MRU同樣釋放 reader；保留原本 immutable cached payload先嘗試同步，再釋放 reader；最後一位離開時加入 MRU
TaskFallbackFallback lease −1；結果可使用；不發布 cacheFallback lease −1；不改 cache先嘗試同步，再釋放 fallback lease；不改 cache

淘汰後填入失敗

一旦新 key 已取得 CacheFill，舊 key 已經被淘汰。新 fill 失敗後 entry 回 Empty，不會恢復舊 cached 資料。之後任一 key 再來都可重新填入。

同時有多位 reader

Reader 不互相排斥，且都只能讀。任何一位成功、失敗或 abort 都只減少自己的 lease；還有人在讀時，entry 持續受到保護。

// 示意：H2D、kernel、D2H 都使用 resources.stream
GpuCacheRequest request;
request.gpuId = resources.gpuId;
request.stream = resources.stream;
request.d_fallback = resources.d_input;
request.fallbackBytes = resources.inBytes;
GpuDataAccess access = staticData.getCacheData(metadata, request);
const CacheStatus status = access.status();
if (status == CacheStatus::Invalid) return false;
const cudaStream_t stream = access.getStream();

bool ok = true;
if (status == CacheStatus::CacheFill || status == CacheStatus::TaskFallback) {
    ok = enqueueH2D(access.writableData(), stream);
}
if (ok) {
    ok = enqueueComputeAndD2H(access.data(), stream);
}
// 提交失敗也要呼叫，讓已提交的工作同步並結束 lease。
if (!access.freeCacheData(ok)) return false;
// 這裡才能收集 D2H 結果；access 的指標已不可使用。
重複呼叫、發布失敗，以及同步的邊界

正常路徑只呼叫一次。Default Invalid access 或已完成的 access 呼叫 freeCacheData() 會回傳 false；收尾後 status() 為 Invalid、getStream() 為 nullptr，所有指標不可再用；已 reset 的 access 析構不再同步。Access 不可複製或移動。

Fill 若無法標記 replica 有效，或無法加入 LRU，會回滾至 Empty 並回傳 false。Manager 會檢查 owner、key、pointer、bytes、狀態與 lease 計數；內部驗證失敗不視為成功發布，也不能假設受損的計數已修復。

正常收尾會檢查 CUDA 同步結果；析構是錯誤路徑的保護網，會嘗試同步並記錄 CUDA 錯誤後 abort，無法回傳成功結果。它不會把未完成的 fill 發布成 Valid。Cache mutex 保護管理狀態；CUDA 工作在各 task stream 執行，收尾時的同步發生在 manager 的狀態鎖之外。

Miss 由 caller 處理。 Frame 的 CacheFill／TaskFallback 要 H2D；result 則由算法產生資料。GpuCacheRequest 提供 GPU、stream、fallback pointer 與容量；GpuDataAccess 回傳 status 與同一條借用的 stream。全部工作結束後才發布，不需額外 H2D event。目前 demo 僅使用 frame cache；result 的版本識別與重算策略由 caller 定義。
呼叫端的責任：成功 flag 代表所需 H2D、compute、D2H 已正確提交；cache 不檢查影像內容。相同 key 的內容若改變，需使用新 identity 或先在安全邊界 reset。Frame demo 以 task d_input 作 fallback；每次 request 明確提供 fallback pointer 與容量。Frame／result 同時存取時必須使用不會互相覆寫的空間，不同 cache instance 可有不同 payload 大小；目前 graph 以 task exclusive checkout 防止跨 worker 重用同一 task。
05

從初始化到關閉，什麼會被清掉？

操作允許時機Mapping / 狀態GPU 配置
initialize / init尚未初始化；一顆合法 GPU；有效 layout / bytes；配置成功建立固定索引與 K 個 Empty entries預配置 K 個 cache buffers；task 資源另行配置
freeCacheData(ok)持有有效 access依上表發布、釋放 reader 或回滾保留
resetCache()已初始化、未 release，且沒有 cache / fallback leases、沒有 Loading清除 mapping、metadata、replica validity、LRU；全部回 Empty保留原 pointer；下次存取需要重新上傳
release()沒有任何 live lease，也沒有 Loading釋放成功後清空索引及管理資料，變成未初始化釋放 entry 的 GPU 配置；task d_input 由 task 資源生命週期釋放

有 live fallback 也不能 reset / release，包含 K = 0。 正常在 phase / run 的 quiescent boundary 重設，先完成所有 access，再關閉 owner 與 task resources。

生命週期的失敗與重試

初始化會拒絕重複初始化、多顆 GPU、無效 GPU ID / bytes、容量計算溢位或配置失敗；StaticData 從 framework 提供的目前 NUMA 環境查詢 GPU，零顆或多顆都拒絕，並檢查固定 layout 的 bytes 與可用 GPU memory。K = 0 是合法設定。

Reset 的前置條件不成立就回傳 false，不清除 cache。Manager release 遇到 live lease 或正在 release 也回傳 false。完全釋放後重複 release 回傳 true。

實際釋放配置時若 CUDA release 失敗，會回傳 false；仍未釋放的 entry 保留供重試，manager 停止提供新存取。StaticData::release() 在呼叫 manager 前就先把自己的 initialized 設為 false，因此即使因 live lease 被拒絕，也不能再透過 StaticData 取得新 access；先結束現有 lease，再重試 release。Owner 必須活得比所有 access 久。

06

容量固定，到達的 frame 數可以一直增加

N、K、S 是不同的數量

N 是先後到達的 frame 數；K 是 GPU cache entry 數；S 是 CPU residency table 的 slot 數。

S = K == 0 ? 0 : nextPow2(2 × K)

索引只保存現在 Loading / Valid 的 key，最多 K 筆。淘汰時 erase 舊 key、insert 新 key，所以 N 大於 K 或 S 仍可持續運作。預設 K = 4。

試算 cache 配置

4最多 resident keys
64 MiBCache GPU bytes

只算 cache；task fallback、staging 與算法配置另計。

Hash collision、刪除與 LRU 的完整規則

Residency table 保存 key → entryIndex。Hash 到相同 slot 時，以 linear probing 找完整 key 或空位；遇到空位表示 miss。Collision 不會讓不同 camera / frame 共用資料。Erase 使用 backward shift 維持 probe chain，讓後面的 key 仍能找到。

K > 0 時 S ≥ 2K，最多一半 slots occupied；Loading 也占一筆 mapping。Slots 在初始化配置，hot path 不 grow / rehash。查找平均 O(1)，最壞可達 O(S)；平均值不是固定延遲保證。

Empty pool 優先於 LRU。Global LRU 是這個 manager 共用的一條 list，與 hash slot 排列無關；由左至右可理解為 LRU → MRU。首次 hit 移出 entry，最後一位 reader 結束後才放到 MRU；fill 成功也放到 MRU。所以可淘汰順序取決於 lease 結束時間，並非單純的 request 到達順序。

淘汰、失敗回 Empty、reset 都不重新配置 GPU buffer。Hot path 沒有 cudaMalloc() / cudaFree()；真正的配置與釋放在生命週期邊界。
