Incoming Frame 如何使用 GPU Cache

這份頁面完整說明 K、GpuCacheEntry、fixed open-addressing GpuResidencyTable、global LRU，以及每個 incoming frame 如何得到 CacheHit、CacheFill 或 TaskFallback。

核心不變：cache 不參與 graph scheduler 選擇

先分清楚三個數字

N：Incoming／logical frames

例如 N = 220

代表一個 run 中要處理多少個 FrameCpuAtom。N 可以遠大於 K，不需要先建立 frame registration list，也不決定 cache GPU buffer 數量。

K：GPU cache capacity

K = gpuCacheEntries

代表固定配置多少個 GpuCacheEntry。最多只有 K 個 key 能同時處於 resident 或 loading；目前預設 K = 4，K = 0 表示停用 cache。

S：Residency table slots

S = nextPow2(2 × K)

S 是 CPU-side lookup slots，不是 frame 數，也不是 GPU buffer 數。表內最多放 K 筆 mapping，因此 load factor 不超過 50%。

重要：2 × K 是「K 的兩倍」，不是 2K bytes，也不是固定的 2048。K = 4 時 S = 8；即使 N = 220，table 仍只有 8 slots，而且最多只有 4 slots occupied。

每一層到底保存什麼

FrameCpuAtom 每個 logical frame 一份

  • 擁有 immutable CPU input bytes。
  • 擁有 FrameMetadata 與 JobResult。
  • cache miss 或 fallback 時可重新 H2D。

StaticData 每個 graph copy 一份

  • 保存固定 frame layout，並提供 graph-copy resetCache()。
  • 接受任何相符 incoming key；不保存 N-frame registry。
  • 擁有一個 GpuCacheManager。

GpuResidencyTable S 個 CPU slots

  • 只保存 GpuDataKey → entryIndex。
  • 不保存 frame bytes，也不擁有 GPU allocation。
  • fixed open addressing；hot path 不 grow／rehash。

GpuCacheEntry 固定 K 份

  • 擁有 persistent GpuReplica.d_data。
  • 保存目前 cached metadata、state、lease count 與 LRU links。
  • 被 LRU 替換時重用同一個 device pointer。

TaskGpuResources 每個 task instance 一份

  • 擁有 stream、pinned staging、scratch 與 algo-private buffers。
  • 擁有 persistent fallback d_input。
  • fallback 保證 cache 不可用時仍可正確執行。

DummyGraph scheduler owner

  • 管理 ready、in-flight、terminal 與 phase collections。
  • 先選 frame、task instance、NUMA-local worker，之後才查 cache。
  • 不根據 cache hit／miss／GPU residency 改變選擇。

失敗或 RAII abort：fill mapping 被 erase，entry 回到 Empty；不發布壞資料。
CacheHit

已經有可讀 GPU copy

  1. 不做 H2D。
  2. algorithm 讀 cache entry device pointer。
  3. lease 期間不可 eviction。
  4. 完成後更新 global LRU recency。
CacheFill

Miss，但 cache 有可用 entry

  1. Empty 或 LRU victim 被保留。
  2. 舊 mapping erase，新 mapping insert。
  3. CPU atom H2D 到 cache buffer。
  4. 成功同步後才發布 Valid。
TaskFallback

Cache 暫時不可使用

  1. 使用 task-private persistent d_input。
  2. CPU atom 重新 H2D。
  3. 照常 compute 與 D2H。
  4. 不新增或破壞 cache residency。

Table key 是完整的 GpuDataKey(frameId, cameraId)，value 是穩定的 entryIndex。下圖是 K = 4、S = 8 的示意；occupied 位置由 hash 與 linear probing 決定，不代表 entry 本身存放在該 CPU slot。

Find：平均 O(1)hash(key) & (S - 1) 找 home slot；collision 時向後 linear probe，遇到 empty 即代表 miss。
Insert：固定 slotsCacheFill 才 insert。最多只有 K 筆 mappings，且 S ≥ 2K，因此至少一半 slots 保持 empty。
Erase：backward-shift deletion淘汰或 fill abort 時 erase；必要時將 probe cluster 後方元素前移，不留下長期累積的 tombstones。
為何不用 std::unordered_map所有 slot 在 init 預配置；hot path insert／erase 不建立 node、不 grow，也不 rehash，CPU memory 與延遲有固定上限。

平均複雜度是 O(1)，理論 worst case 仍可能探查多個 slots。以最大 50% load factor 降低 collision chain，是用少量固定 CPU metadata 換取穩定 hot-path 行為。

多個 frames 同時進來時

Valid 且 inactive存在 global LRU，允許成為 victim。
Valid 且 activeAccesses > 0暫時不在 LRU，reader lease 保護 device pointer，不可 eviction。
Loading正在填入的 entry 不在 LRU。另一個 task 要同一 key 時不等待，直接 fallback。
所有 K entries 都 active/loading沒有可替換 victim；新 frame 使用自己的 task fallback，不修改 cache。
這是 best-effort cache：同時 live frames 超過 K 不會造成 correctness failure，只會增加 fallback H2D。前提是原始 payload 能從 immutable FrameCpuAtom 重建。

Scheduler 與 GPU cache 的邊界

Worker 只綁 NUMA一個 task instance 可以在不同 NUMA-local workers 上依序執行。
Task instance 固定綁 GPUstream、fallback、scratch 與 algo-private buffers 仍屬於 task instance。
Cache 不選 task 或 GPUscheduler 先完成 assignment；cache 只根據已選 task 的 GPU resources 回傳 data access。
目前一張 GPU／NUMA介面保留 GPU ID 與 replica 結構；兩張 GPU／NUMA 的 P2P／replica migration 尚未實作。

Correctness 前提與目前限制

目前 cache 保存 immutable frame inputEviction 後可從 FrameCpuAtom 重新 H2D，因此 hit 只影響效能，不影響結果。
Mutable GPU-only intermediate 不可直接套用若資料無法從 CPU 重建，必須增加 authoritative frame-owned storage、spill/recompute contract，或保證足夠容量。
一個 task 目前只有一個 fallback input若同一次 execute 必須同時持有 master/reference 且兩者都 fallback，需要兩個獨立 fallback slots 或 caller-provided buffers。
K 應由量測決定觀察 hit、fill、fallback、eviction 與 reuse distance。增加 K 只應改善效能並增加 VRAM，不應改變 correctness。
